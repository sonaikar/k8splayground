# Cilium Gateway API + MetalLB on Multipass

This document captures the full setup, validation, and troubleshooting flow used to expose the `guestbook/frontend` app through **Kubernetes Gateway API** with **Cilium** and **MetalLB**.

## Goal

Expose HTTP traffic to `guestbook/frontend` using:

- Gateway API (`GatewayClass` + `Gateway` + `HTTPRoute`)
- Cilium as Gateway controller and L7 proxy
- MetalLB to assign a `LoadBalancer` IP on bare-metal/VM networking

---

## Files in this folder

- `gatewayclass.yaml` - Gateway class handled by Cilium
- `gateway.yaml` - L4 listener (`HTTP :80`) in `guestbook`
- `httproute.yaml` - L7 route to `frontend` service
- `metallb-ippool.yaml` - MetalLB address pool + L2 advertisement
- `cilium-envoy-config.yaml` - manual/debug Envoy config (normally auto-generated by Cilium)

---

## Architecture

```text
Client (Host)
   |
   | HTTP
   v
MetalLB VIP (e.g. 192.168.252.100)
   |
   v
Service: cilium-gateway-frontend (LoadBalancer, selectorless)
   |
   v
Cilium eBPF redirect -> Envoy listener (synthetic EndpointSlice: 192.192.192.192:9999)
   |
   v
HTTPRoute rules
   |
   v
Service: guestbook/frontend:80
   |
   v
frontend pods
```

## Prerequisites

- Kubernetes cluster running on Multipass VMs
- Cilium installed and healthy
- Gateway API CRDs installed (GA `v1` present)
- MetalLB installed and healthy
- `guestbook/frontend` service and pods running

Useful checks:

```zsh
kubectl get nodes
kubectl get crd | grep gateway.networking.k8s.io
kubectl -n kube-system get pods | grep -E 'cilium|cilium-envoy|cilium-operator'
kubectl -n metallb-system get pods
kubectl -n guestbook get svc frontend
kubectl -n guestbook get pods
```

## Install/enable components

## 1) Gateway API CRDs (required by Cilium Gateway controller)

Use a modern release that includes `v1` resources:

```zsh
kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.2.1/standard-install.yaml
kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.2.1/experimental-install.yaml
```

Verify `v1` is present:

```zsh
kubectl get crd gatewayclasses.gateway.networking.k8s.io -o jsonpath='{.spec.versions[*].name}'
kubectl get crd gateways.gateway.networking.k8s.io -o jsonpath='{.spec.versions[*].name}'
kubectl get crd httproutes.gateway.networking.k8s.io -o jsonpath='{.spec.versions[*].name}'
kubectl get crd grpcroutes.gateway.networking.k8s.io -o jsonpath='{.spec.versions[*].name}'
```

## 2) Cilium Gateway API support

Cilium config should show Gateway enabled:

```zsh
kubectl -n kube-system get configmap cilium-config -o yaml | grep -i enable-gateway-api
```

If needed:

```zsh
helm upgrade cilium cilium/cilium \
  --namespace kube-system \
  --reuse-values \
  --set gatewayAPI.enabled=true
```

## 3) MetalLB

Install MetalLB:

```zsh
kubectl apply -f https://raw.githubusercontent.com/metallb/metallb/v0.14.9/config/manifests/metallb-native.yaml
kubectl -n metallb-system rollout status deployment/controller
kubectl -n metallb-system rollout status daemonset/speaker
```

Apply pool config from this repo:

```zsh
kubectl apply -f /Users/ssonaika/git/k8splayground/gatewayapi/metallb-ippool.yaml
```

## Validate end-to-end

## 1) Gateway objects

```zsh
kubectl get gatewayclass
kubectl -n guestbook get gateway frontend -o wide
kubectl -n guestbook get httproute frontend -o wide
kubectl -n guestbook describe gateway frontend
kubectl -n guestbook describe httproute frontend
```

Expected:

- `GatewayClass cilium` exists
- `Gateway frontend`: `Accepted=True`, `Programmed=True`, `ADDRESS=<VIP>`
- `HTTPRoute frontend`: `Accepted=True`, `ResolvedRefs=True`

## 2) Generated service and endpoint wiring

```zsh
kubectl -n guestbook get svc cilium-gateway-frontend -o wide
kubectl -n guestbook get endpointslice cilium-gateway-frontend -o yaml
kubectl -n guestbook get ciliumenvoyconfig
```

Notes:

- `cilium-gateway-frontend` is selectorless by design.
- EndpointSlice showing `192.192.192.192:9999` is expected for Cilium's internal proxy path.

## 3) Traffic tests

From inside cluster (curl pod or debug pod), test:

```zsh
curl -v http://<gateway-vip>
curl -v http://cilium-gateway-frontend.guestbook.svc.cluster.local
```

From host, test external VIP:

```zsh
curl -v http://<gateway-vip>
```

## Important behavior in this environment (Multipass on macOS)

Observed and confirmed:

- Gateway and route worked from inside cluster and node debug pods.
- ARP resolution and ping to MetalLB VIP failed from macOS host.

This indicates a **host/L2 reachability limitation** with floating VIP advertisement in this VM networking setup, not a Kubernetes route misconfiguration.

### What still works reliably

- NodePort from host (`curl http://<node-ip>:<nodeport>`)
- In-cluster access to Gateway VIP

### Recommended practical workaround

Use a stable host-reachable entrypoint (existing load balancer node in Multipass) forwarding to NodePort, rather than relying on host-side ARP for floating VIPs.

## Troubleshooting guide

## A) Gateway stuck `Waiting for controller`

Check:

```zsh
kubectl get gatewayclass
kubectl -n kube-system logs -l app.kubernetes.io/name=cilium-operator --tail=100 | grep -i gateway
```

Fix:

- Ensure Gateway API CRDs include `v1`
- Ensure Cilium Gateway API is enabled
- Ensure `GatewayClass cilium` exists (manual apply if auto-creation fails)

## B) Cilium operator error about missing `TLSRoute` / wrong API version

Cause:

- CRD version mismatch (older CRDs with no required `v1`, or downgrade attempt blocked)

Fix:

- Install compatible Gateway API bundle with `v1` resources (e.g. `v1.2.1`)
- Restart `cilium-operator`

## C) `kubectl port-forward svc/cilium-gateway-frontend ...` fails

Expected for selectorless service:

```text
invalid service ... Service is defined without a selector
```

Use in-cluster curl pod / node debug pod / direct VIP tests instead.

## D) Host can’t reach VIP, but pods can

Likely host/L2 ARP limitation in virtualization network path.

Verify:

```zsh
arp -an | grep <vip>
ping -c 3 <vip>
```

Workaround:

- Use NodePort from host
- Or front NodePort with stable LB node IP
